## 1. 技术选型

### D1 学生模型：Qwen/Qwen3-1.7B

- **备选**：Qwen2.5-1.5B-Instruct（精确 1.5B）、Qwen3-0.6B（更小更快）
- **理由**：①「1.5B 左右」经确认为非硬指标，取最贴近的 1.7B；②**与老师同家族同 tokenizer**（机制见下）；③ Ollama / LLaMA-Factory / Transformers 全链路支持成熟
- **同 tokenizer 的好处**：机制推导见下方 D1.1——一句话版：token 编号是师生共享的坐标系，C 层蒸馏搬运的是老师对每个候选词的「犹豫清单」，坐标系不同清单就作废
- **风险**：若被要求精确 1.5B，Qwen2.5 与 Qwen3-8B 的 tokenizer 兼容性需先验证

#### D1.1 同 tokenizer 为什么是硬前提（完整机制）

先建立直觉。语言模型每生成一个字，其实在做一件事：对整个词表（Qwen3 约 15 万个 token）逐一打分，分数就是 logits，softmax 之后变成概率分布。「猫」得 8.2 分、「狗」得 7.9 分、「鱼」得 1.1 分——模型输出的从来不是一个答案，而是一整张犹豫清单。

白盒蒸馏搬运的就是这张清单。问题来了：全词表存储太贵——7473 条样本 × 512 个位置 × 15 万词表 × 4 字节 ≈ 2.3 TB，显然不行。于是压缩成 top-32：每个位置只留分数最高的 32 个「token 编号 + 分数」，2000 条只要 65MB。这个压缩能成立的前提只有一条：token 编号必须是一个共享的坐标系——老师在坐标 37216 处打的分，学生在同一个坐标 37216 处也能找到对应的 token。

**同 tokenizer**：坐标系完全相同。老师传给学生的不再是「答案是猫」（one-hot，这是普通 SFT），而是「猫 8.2 分、狗 7.9 分、鱼 1.1 分」——「猫但差点选狗、绝不是鱼」这种候选之间的相对关系，就是暗知识。这是蒸馏超越普通微调的全部价值所在。

**不同 tokenizer，三级失效**：① 编号错义——坐标 37216 在老师词表里是「猫」，在学生词表里是「苹果」，学生取出来的分数是垃圾，KL 在优化一个幻觉；② 粒度错位——同一段话老师切 4 个 token、学生切 5 个，从第二个位置起全部错位，需要动态规划做对齐，边界合不上的地方只能合并分布，每合并一次就有损一次；③ 词表缺口——老师 top-32 里可能有学生词表里压根不存在的 token，这些候选直接蒸发。

**精确边界**（与 D3 咬合）：B 层（学推理链）的信号是纯文本，学生的 tokenizer 重新切分老师的答案即可，跨 tokenizer 也能做；真正被同 tokenizer 锁死的是 C 层。同家族选型让 B、C 共用一套数据格式，还附赠对话模板同源、零额外变量。

### D2 老师模型：Qwen/Qwen3-8B

- **备选**：Qwen3-4B（更省显存，三级蒸馏的中间层备选）
- **理由**：① 8B 规模的推理与生成在远程昇腾 910B 上余量充足；② 与学生同 tokenizer（机制见 D1）；③ 全链路证据最足的成熟路线——本地冒烟测试已用 Qwen3 系在 LLaMA-Factory 跑通，一周任务优先选零未知风险的路径
- **进阶结论（已验证）**：曾假设 8B→4B→1.7B 的中间助教可以缓解容量鸿沟；实际串行工程版级联与原始 4B 直教数学完全打平、通用无显著差异。因此级联不再是待决定事项；若继续研究，应转向独立传递集或更大数据，而不是默认级联有效。

#### D2.1 「甜点位」与容量鸿沟（完整机制）

「甜点位」是规划期的算术题：按最初设想的 24GB 级显卡计算，8B FP16 权重 16GB 装下后余 8GB 给 KV cache——刚好够，8B 是当时规划算力上能从容推理的老师尺寸。实际执行部署在昇腾 910B 服务器（大显存 NPU），余量更充足，模型选型结论不变。

容量鸿沟则是另一个问题：软标签要教的是「15 万维上完整的分布形状」。学生容量小，表达能力有上限，只能拟合分布的主峰，丢掉尾部的精细区分——老师对两个近义词之间 0.1 分的犹豫，学生可能根本没有对应的表征去承接。4.7:1 的比例意味着这种丢失会很明显。三级蒸馏的思路是让 4B 先把分布「压扁」一次（4B 学 8B 的分布，比 1.7B 容易得多），学生接手一个已经简化过的教学目标——这也是它只能当进阶选项的原因：多一倍老师生成成本。（2026-10-02 实测补记：在 460 条规模上，真级联（8B→4B 助教→1.7B）与直接用原始 4B 教 1.7B **完全打平**——数学逐题 17/17 互 flip、p=1.0，通用 −1.5pt、p=0.53；「先压扁」这一步没有可测贡献。反而是教师容量本身出了显著效应：原始 4B 软标签直教的通用卷显著高于 8B 软标签直教（+4.25pt，p=0.033），数学持平——更贴近学生容量的老师信号更温和。详见结果速览「级联与教师容量对照」。）

### D3 蒸馏范式：先 B 层（学推理链），后 C 层（学 logits 分布）

- **备选**：A 层（只学答案，严格说不算蒸馏）；A+B+C 一步到位
- **理由**：B 层数据形态是「问题→思考→答案」，LoRA SFT 即可落地，先拿端到端结果；C 层再叠加 KL 项
- **选层的侧重性（2026-09-25 补记）**：B 先 C 后是刻意侧重——① B 层 LLaMA-Factory 原生支持，**C 层需要自定义训练循环**（离线预计算 logits + 自写 KL loss，LLaMA-Factory 不支持），工程量高一档；② C 层的收益点（校准度、暗知识）在 300 题判对率上未必可见，投入产出比差；③ A 层被排除是因为「用现成答案微调」不构成蒸馏实验
- **Loss**：`L = a·T²·KL(p_T ‖ p_S) + (1-a)·CE`，起步 T=2.0、a=0.7；**KL 项必须乘 T²**（推导见 D3.1）。当前存档只保留老师 top-32，因此实际实现是师生都在该 top-32 集合内重新归一化后的**条件 KL**，不是完整词表 KL
- **C 层历史约束与当前选择**：最初按 24GB 级单卡规划时，8B 老师 + 1.7B 学生无法安全同场（算术见 D4.2），所以设计为离线预计算 top-k=32 logits。实际远程 910B 的 60GB 级显存理论上可以在线共驻，但现有 460 条 logits 已采集并验证完成；继续采用离线 KL 可避免重复老师 forward，也更利于复现

#### D3.1 KL 项为什么必须乘 T²（推导）

softmax 使用温度 `T` 时，logit 先除以 `T`，所以 token 之间的相对差异被压缩，概率分布变平。高温下 soft-target loss 的梯度量级近似按 `1/T²` 缩小。如果不做补偿，把 T 从 1 调到 4，软标签那一路的梯度会**悄悄**缩小 16 倍——表面上是「我在调分布的软硬」，实际上蒸馏信号被 T 这个旋钮静默吞掉了，实验现象会变成「T 越大越没用」，而真相是你把学习率间接砍掉了。

乘 T² 之后，调 T 主要改变「教什么」（分布的软硬、哪些暗知识被保留），不改变「学多猛」（梯度量级），两个旋钮解耦——实验才可归因。这一处理来自 [Hinton 等人 2015《Distilling the Knowledge in a Neural Network》](https://arxiv.org/abs/1503.02531) 的高温梯度分析。

#### D3.2 「离线预计算」的本质

最初按 24GB 级显卡规划时，16GB（老师权重）+ 3.5GB（学生权重）已经 19.5GB，再加 LoRA 梯度与优化器、激活和 KV cache，在线同场没有安全余量。离线化把「老师授课」和「学生上课」拆成两个时间阶段，中间用 logits 文件做介质：老师只需要讲一次课，学生可以反复训练。当前 460 条 top-32 原料每位老师约 57MB JSONL、16MB gzip。远程 910B 后来具备在线共驻的显存条件，但离线方案仍能省去重复 teacher forward，并冻结老师信号，便于 CE/KL 对照复现。

#### D3.3 一条样本如何完成 forward → CE/KL → backward

C 层不是把一整段文本直接“塞进模型就结束”，而是对每个答案 token 做 next-token prediction。设题目对话模板编码后长度为 `P`，老师解答编码后长度为 `S`：

```text
input_ids                         [prompt_ids + solution_ids]   长度 P+S
学生 forward 的 logits             [P+S, vocab_size]
用于预测答案的 logits              logits[P-1 : P+S-1]          长度 S
答案硬标签                         input_ids[P : P+S]           长度 S
教师软标签                         每个答案位置的 top-32 token/logprob
```

为什么从 `P-1` 开始？因果语言模型在位置 `t` 输出的是“下一个位置的 token”分布，因此 prompt 最后一个位置负责预测第一个答案 token。这个切片正是 `scripts/kl_train_4b.py` 中 `prediction_logits` 与 `targets` 的对齐关系。

然后有两条损失路径：

```text
CE：学生完整词表 logits → 正确答案 token
KL：学生 logits gather 教师保存的 32 个 token → T=2 的 softmax
```

教师文件保存的是 log-probability，不是 raw logits；训练时教师分布先除以 T 再 softmax，学生分布也在同一组 token 上做 `log_softmax`。由于只保存 top-32，二者都在这 32 个候选内重新归一化，所以实际是**top-32 条件 KL**，不是完整词表 KL。教师概率调用 `detach()`，不接收梯度；梯度只从总 loss 回到学生。

```text
loss = alpha * T² * KL + (1-alpha) * CE
      ↓ loss.backward()
PyTorch autograd 沿计算图反传
      ↓
LoRA A/B 低秩矩阵（基座权重冻结）
      ↓
梯度裁剪 → AdamW → cosine scheduler
      ↓
保存 LoRA adapter
```

C 层默认 `alpha=0.7`、`T=2.0`、`lr=5e-5`、梯度累积 8。梯度累积和梯度检查点不是一回事：前者是多条样本反向后再更新一次，模拟更大的有效 batch；后者是不保存全部中间激活、在反向时重算，主要用计算时间换显存。

这也解释了训练和评测的区别：训练使用 `model(...)`、teacher-forcing、loss 和 autograd；评测使用 `model.generate(...)`、`no_grad()` 和判卷，不会更新参数。训练结束保存的是 adapter，后测时再把 adapter 挂回同一个 Qwen3-1.7B 基座。

#### D3.4 停尾 token：为什么"学会答题"不等于"学会停下"（2026-09-30 实测发现）

C 层实测暴露了一个训练目标上的盲区：**我们的自定义训练循环从不监督"答案写完之后该输出什么"**。

机制上很清楚：训练样本是 `prompt + solution`，监督只覆盖解答 token（`logits[P-1 : P+S-1]` 对 `targets[P : P+S]`），而"预测最后一个解答 token 之后那个 token"的位置根本没有进入损失——那个位置恰好就是该收尾的地方（Qwen3 对话格式里的 `<|im_end|>`）。CE 项只教"下一个解答 token 是什么"，KL 项也只覆盖解答 token 位置上的候选分布，两者都没教"什么时候停"。

对照证据很干净：CE 控制组在冻结考卷上有 **75%** 的题跑满 2048 token 也不停止（其中不少是"答案已写出、后面继续啰嗦"），而基线 24%、8B-KL 组 21.3%；历史 v1 用 LLaMA-Factory 的 SFT 训练时白卷率是 **0%**——因为框架的对话模板会把 `<|im_end|>` 放进监督目标里。

两项推论都做了实测（2026-10-01）：把训练序列末尾补上 `<|im_end|>`（CE 覆盖 S+1 个位置、KL 仍只用前 S 个位置）重跑两组后，考卷二截断率 CE 组 75%→**0%**、KL 组 21.3%→**1%**，而准确率没有统计上可辨的变化（CE −2 题 p=0.85、KL 0 题 p=1.00）。所以这项监督修的是"会不会停"这个**行为**，不是"答得对不对"这个**能力**——答案在被截断之前基本都已写出；它真正的价值是生成行为正常化（不再空烧 2048 token）与评测口径干净。

更一般的教训：**训练目标的"覆盖范围"和"损失函数的形式"是两件事**。容易只盯着 CE/KL 的选择，却忽略监督信号在序列上覆盖到哪里——没覆盖的位置，模型只能靠预训练习惯去猜。

### D4 算力分工：B 层先本地闭环，C 层迁移到远程 910B

- **历史方案（B 层已执行）**：8B 老师在远程生成文本，本地 4060 完成 1.7B LoRA 与双卷评测。这样最初能把远程环境变量降到最低，便于快速迭代
- **当前方案（C 层，2026-09-28 调整）**：本地电脑不再承担计算，logits 训练和后测全部迁移到远程 910B。采用**离线 KL**：老师的 top-32 分布已经采成约 16MB gzip 文件，训练时只加载 1.7B 学生，不需要 8B 老师与学生同时驻留
- **为什么不优先在线共驻**：910B 的 60GB 级显存理论上能同时装下 8B+1.7B，但已有离线 logits 后，在线方案会重复老师 forward，并把 vLLM 推理栈、Transformers 训练栈和反向传播绑在同一进程，成本和故障面都更大，没有新增实验信号
- **环境边界**：实际在 `develop-llm-npu` 专用容器中使用匹配 CANN/驱动的 Ascend PyTorch（`torch_npu`）完成 C 层训练和评测；不直接改动稳定工作的 vLLM-Ascend 推理容器。探针、真实模型对齐、冒烟和全量训练均已完成。执行命令和复现边界见 [项目总览.md](../项目总览.md) 与 [C层远程执行手册.md](C层远程执行手册.md)。

#### D4.1 CUDA 与 torch_npu：同一 PyTorch 抽象的不同后端

本地 B 层使用 WSL2 + RTX 4060 + CUDA，远程 C 层实际使用昇腾 910B + `torch_npu` 完成训练和评测。两边都可以执行相同的高层流程：

```text
tokenizer → Transformers forward → loss → autograd backward → LoRA/AdamW
```

不同之处在底层设备和软件栈：CUDA 对应 NVIDIA 驱动，`torch_npu` 对应 Ascend CANN 和 NPU 驱动。`scripts/probe_npu_train.py` 会实际测试 BF16、gather、log-softmax、CE、KL、backward 和 AdamW step，但它只使用小张量，不加载 Qwen3-1.7B；探针通过不等于真实模型训练已经完成。

#### D4.1.1 为什么从 4060 搬到 910B 后要重新测基线

B/A 线原先在 RTX 4060 + CUDA 上训练和评测；C 层因为训练环境迁移到远程昇腾 910B，所以训练和后测改用 `torch_npu`。即使仍然是同一个 Qwen3-1.7B、同一份考卷、同一个 prompt 和贪心解码，CUDA 与 NPU 的算子实现、BF16 数值路径、padding/批处理和生成内核也可能让结果发生偏移。

因此不能直接这样算：

```text
NPU 训练后分数 − CUDA 训练前分数
```

这样算出来的差值混合了两种因素：

```text
模型经过蒸馏后的变化
+
从 CUDA 换到 NPU 的平台变化
```

正确做法是先把**未训练的同一个基座模型**放到 NPU 上，按正式冻结协议跑一遍，得到 C 层自己的设备内零点：数学 `0.7467`、通用 `0.6175`。旧 CUDA 前测 `0.7600 / 0.6400` 仍然保留，但只作为迁移前参考；实测设备偏移为数学 `-1.33pt`、通用 `-2.25pt`。

所以三种比较分别回答不同问题：

- `NPU 未训练基线 − CUDA 历史基线`：换设备本身造成了多少偏移；
- `NPU adapter − NPU 未训练基线`：训练整体带来了什么变化；
- `NPU KL − NPU CE`：在同一 NPU、同一训练循环中，top-32 软标签相对纯 CE 有没有额外收益。

这次重测不是新增训练组，而是**平台迁移校准**。如果跳过它，后面的蒸馏效果就无法区分是模型学到了东西，还是设备后端改变了分数。

远程实验的权限边界已经解决：老师同意使用支持反向传播的 `llamafactory-npu` 训练容器。执行前仍要先做只读确认（`docker inspect` 看挂载、`npu-smi info` 看容器内可见卡与占用），不能因为服务器上存在某个容器就默认有权启动或改动它——`vllm-ascend` 仍然只用于老师推理与 logits 采集。

#### D4.2 显存算术（两个「为什么」的完整版）

**老师为什么本地跑不了**：8B 参数 FP16 = 16GB 权重，4060 总共 8GB 显存，还没算 KV cache 和框架开销，第一步加载权重就爆了——这不是优化能救的，是物理装不下。远程 910B 大显存推理 16GB 权重余量充足，推理成立。

**学生为什么本地训得动**：1.7B FP16 权重 3.5GB；LoRA 只训外挂的小矩阵（rank=8 时约 20MB 级），梯度和优化器状态合计 ~0.3GB；开梯度检查点后激活值从「随深度线性堆积」变成「只存检查点、反向重算」，压到 1-2GB。合计 5-6GB，8GB 的卡留有余量。这三个数字就是冒烟测试实测配置的出处（loss 正常下降、无 OOM，实验记录 #3）。

#### D4.3 为什么 vLLM 不放 WSL2（三层坑的机制与不确定性）

1. **依赖锁死**（确定性高）：vLLM 的自定义 CUDA 算子与特定 torch/CUDA ABI 预编译绑定，装它 = 新建 venv + 2-3GB 依赖，与现有训练环境互斥
2. **GPU-PV 半虚拟化层缺口**（机制成立、细节未验证）：WSL2 的 CUDA 走 /dev/dxg 穿透到 Windows 驱动执行，标准 CUDA 可用，但 vLLM 依赖的 Triton 运行时编译、CUDA graph capture、底层显存管理 API 对驱动行为敏感，社区在 WSL2 上集中报告过 EngineCore failed / Triton 编译失败。诚实标注：具体缺口当前版本是否还存在未验证——vLLM 近年把大量内核路径改成了标准 PyTorch API，支持在改善
3. **显存预分配与 P15 悬崖正面相撞**（确定性高）：vLLM 启动时按「可用显存 90%」一次性预分配常驻池；WDDM/GPU-PV 环境下可用显存受桌面动态影响报数不准，8GB 卡上 Windows 图形栈（Steam/浏览器/ZCode）都在分显存——HF 按需分配被挤只是变慢，vLLM 预分配被挤是启动 OOM 或运行期崩

为什么远程 910B 上没这些问题：原生 Linux + 独占大显存算力（无桌面分显存）+ 干净依赖环境——远程推理引擎的原生栖息地。这也是「vLLM 放远程」策略的完整逻辑：不是 vLLM 神圣，是它的运行条件在远程全满足、在本地全不满足。本地验证成本 = 45 分钟时间盒（新 venv → 冒烟 0.6B）

### D5 基线工具：Ollama（Windows 原生）

- **备选**：直接在 WSL2 用 Transformers 跑基线
- **理由**：免等待训练环境，一条命令出结果；4bit 量化足以建立「学生有多笨」的体感
- **定位与边界**：Ollama/GGUF 只能推理（无反向传播、拿不到 logits），不参与蒸馏本身；**已知混淆变量**——量化基线 vs FP16 学生的起点略有偏差，基线数字不作为精确结论
- **边界精确化**：「不能训练」的原因是**工程栈**不是量化本身——GGUF/llama.cpp 是纯推理栈，没有自动微分、没有优化器；QLoRA 拿 4bit 量化基座训练就是反例（bitsandbytes 有训练用的量化实现）。被问「量化了怎么还能训」时，答案分两层：量化不是障碍，缺的是训练基础设施
- **工具链分工备忘**：Transformers = 学生模型、tokenizer、`forward`/`generate`；vLLM-Ascend = 远程 910B 上老师批量推理和 `prompt_logprobs` top-k 采集；PyTorch = 张量、loss、autograd、优化器；PEFT = LoRA 注入与 adapter 管理；Ollama = 基线体感；GGUF 只能推理不能训练，Ollama 拉的模型不能直接拿来微调

### D6 训练框架：LLaMA-Factory + WSL2

- **备选**：裸 Transformers + PEFT 自写脚本；unsloth
- **理由**：① yaml 配置化微调，内置对话模板与数据集注册，LoRA/QLoRA 开箱即用，学习成本低于自写训练循环；② QLoRA 依赖 bitsandbytes，基本只支持 Linux → 用 WSL2 而非 Windows 原生
- **为什么是 WSL2（备选方案完整对比，2026-09-25 补记）**：
  | 备选 | 结论 | 原因 |
  |---|---|---|
  | Windows 原生训练 | ✗ | bitsandbytes（QLoRA）基本 Linux-only；LLM 训练生态的教程/报错解答以 Linux 为主，踩坑时能对上别人的解法 |
  | VMware 里的 Anolis 虚拟机 | ✗ | **无 GPU 直通能力**，训练用不了 4060 |
  | 双系统 / 纯 Linux | ✗ | 一周学习任务，Windows 主力机不能丢，装机+迁移成本不成比例 |
  | 云 GPU | ✗ | 有导师提供的远程 910B 就不用花钱租；本地 4060 够跑 LoRA |
  | **WSL2** | ✓ | Linux 生态 + GPU 直通（共用 Windows 驱动，实测 nvidia-smi 可用）+ 与远程 Linux 服务器**环境同构**（shell 与训练框架层一致；加速卡层本地 CUDA、远程昇腾 CANN 不同，但 Python 层无感）——本地踩的坑远程大部分复用 + 已有 WSL 2.4.10 基础，一条命令装完 |
- **落盘细节**：代码与数据集放 WSL 家目录，不放 /mnt/d（跨文件系统 IO 慢一个量级）
- **冒烟实测（2026-09-25）**：Qwen3-0.6B + 200 条 GSM8K 自带答案（仅验管道），LoRA r=8 α=16 lr 5e-5，loss 1.794→0.961 单调下降，61.6s 跑完 25 步无 OOM，adapter 20MB 正确保存——**本地训练链路验证通过，上远程前的最后一道关卡已过**。注意：本次装到 transformers 5.8.0（大版本 5），若后续报兼容性错误，第一嫌疑人是它与 LLaMA-Factory 0.9.6-dev 的 API 差异

#### D6.1 工具链分层：从 YAML 到 adapter

本项目有两条学生训练路径，底层组件不同但计算逻辑相通：

```text
B 层文本蒸馏：
数据 JSON + YAML
  → LLaMA-Factory（训练流程编排）
  → Transformers（Qwen3 模型、tokenizer、forward）
  → PEFT（注入 LoRA）
  → PyTorch autograd + CE + AdamW
  → CUDA / RTX 4060
  → LoRA adapter

C 层 logits 蒸馏：
vLLM-Ascend（教师 prompt_logprobs）
  → 离线 top-32 logprob 文件
  → 自定义 kl_train_4b.py
  → Transformers + PEFT + PyTorch（CE + 条件 KL）
  → CUDA 或 torch_npu / NPU
  → LoRA adapter
```

各组件的边界：

- **LLaMA-Factory**：B 层的命令行和 YAML 编排，负责数据注册、模板、训练器和常用微调配置；它不是自动微分库。
- **Transformers**：提供 `AutoTokenizer`、`AutoModelForCausalLM`、模型 `forward`/`generate` 和学习率调度器。
- **PEFT**：把 LoRA 低秩矩阵注入基座，冻结大部分原始权重，并负责 adapter 保存/加载。
- **PyTorch**：提供 tensor、CUDA/NPU device、CE/KL 算子、autograd、`backward()`、梯度裁剪、AdamW 和 scheduler。
- **CUDA / torch_npu**：分别是 PyTorch 在 NVIDIA RTX 4060 和昇腾 910B 上的硬件后端；不是两套蒸馏算法。训练逻辑仍由 Transformers、PEFT 和 PyTorch 代码决定，但算子、驱动和 CANN 兼容性必须分别验收。
- **vLLM-Ascend**：本项目的教师推理/分布采集环境，不承担学生反向传播。现有容器获授权用于推理，不应为了训练直接改装它。

B 层 YAML 中的 optimizer、weight decay 和梯度裁剪等部分由 LLaMA-Factory/训练器托管，不能从未写出的字段反推具体默认值；C 层则在 `kl_train_4b.py` 中显式创建 AdamW、梯度裁剪和 cosine scheduler。两条路径的训练器差异，是 C 层必须设置 `alpha=0` 控制组的原因。

#### D6.2 LoRA 与 adapter 的训练—保存—评测闭环

完整 Qwen3-1.7B 基座权重不直接更新。LoRA 在目标线性层增加低秩增量，概念上可写成：

```text
W' = W + (alpha / r) * B * A
```

其中 `W` 冻结，只训练小矩阵 `A/B`；本项目使用 `r=8`、`alpha=16`、`dropout=0.05`，C 层目标模块为 `all-linear`，B 层 YAML 写作 `lora_target: all`。训练时只有 `requires_grad=True` 的 adapter 参数交给 AdamW，结束后 `save_pretrained()` 保存 adapter 和 tokenizer。

后测并不加载一套新的完整模型，而是：

```text
原始 Qwen3-1.7B 基座
  + PeftModel.from_pretrained(adapter)
  → eval() + no_grad() + generate()
```

因此前测和后测可以保持同一基座，唯一替换的是 adapter；adapter 是可插拔的参数增量，不是独立的 1.7B 模型。

### D7 数据策略：公开数据集当种子 + 老师生成蒸馏目标

- **数据链已执行**：公开集只提供题目种子，答案由教师重新生成；本项目实际采用“问题作种子、教师重新生成答案”的蒸馏方案，不再是待导师确认的分叉。
- **数据流**：公开集采样几百~几千条 → 远程 910B 上老师批量生成推理链 → 筛洗（目标淘汰 20-40%）→ 训练集；同一批数据顺带产出 top-32 logits（C 层）
- **公开集路线三道必修工序**：分层采样选题 / 审题抽查 / **泄漏检查**（公开训练集常见 benchmark 污染，必须对自有测试集查重，否则提分可能是背题）
- **首选 GSM8K**：题短省 token、答案可自动验证（清洗自动化）、难度梯度好，且对症基线暴露的数学稳定性短板
- **铁律**：训练集与测试集严格隔离；淘汰率 20-40%，全通过说明筛得太松
- **两轮设计（无侧重的落地方式）**：第一轮纯 GSM8K 500（唯一可全自动判卷筛洗的域，归因干净）；考卷一（CMMLU/MMLU）当遗忘哨兵——若通用 accuracy 后测显著下降，第二轮混入通用锚点（COIG-CQIA/ultrachat 采样 100-150 题种子 + 老师生成 + 人工抽查）重训做 A/B。通用数据不进第一轮的根本原因：无标准答案 → 无法自动判卷 → 筛洗质量不可控
- **执行状态（2026-09-27，已落地）**：用户在远程昇腾 910B 真实部署 Qwen3-8B，对 GSM8K 数据逐题生成推理链，经 Mac 中转回本地 → 两道清洗工序（用户：去重/缺字段；脚本：179 条 `\boxed{}` 补 `####`、18 条重复块）→ **460 条训练集，100% 以 `#### N` 结尾**，与判卷器对齐。生成端遗留教训：39% 样本格式不统一，说明生成 prompt 未锁定输出格式——下次应直接规定 `####` 结尾。淘汰率 0% 亦可解释：8B 老师对小学数学近乎全对，无错题可筛（见 D7.1 的预期差异备注）

#### D7.1 两条铁律背后的机制

**合成数据自喂为什么会塌（Model Collapse）**：模型生成的数据天然偏向它自己的高概率区——写出来的题模板化、多样性收缩。下一版模型再在上一版的输出上训练，分布的尾部（罕见但真实的场景）逐代丢失，类似近亲繁殖。锚点数据（人写的真实题）的作用是把分布「钉」在真实需求上，不让它漂。

**淘汰率为什么是 20-40%、且「全通过」是红灯**：真实项目的数据质量是长尾分布，一个正常的筛选器必然会筛掉相当比例——淘汰率是「筛子在工作」的信号，不是要凑的 KPI。反过来，全通过只有两种解释：筛太松，或者老师太强而任务太简单（数学域接近后者，所以我们对 GSM8K 的预期淘汰率低于 20-40%，主要来自格式/超长/过程绕——这个预期差异记录在案，防止汇报时被拿来对照通用域经验值）。

### D8 评测协议：三张考卷 + 全要素冻结

- **前测基线（2026-09-27 定稿）**：考卷二 accuracy **0.76**、白卷率 **22.67%**（两次独立运行 accuracy 逐位一致——协议可复现性自证）；考卷一 accuracy **0.64**（MMLU 0.595 / CMMLU 0.685，unparsed 1.5%）。白卷率在 4bit 量化基线上为 20%、FP16 满血上为 22.67%——**思考不收尾是模型固有问题，与量化无关**，蒸馏数据设计对症
- **考卷二（域内卷）**：GSM8K test 抽 300 题（seed=42 冻结）。题量依据：估值的摆动幅度 ±√(p(1-p)/n)，100 题 95% 置信区间 ±10% 会让「提升 10 分」的结论发飘，300 题 ±6% 才立得住。判卷 = `####` 数字抽取 + 数值比对；思考模式开，max_new_tokens=2048，同步记录白卷率/截断率/按步数分层准确率
- **考卷一（通用卷）**：CMMLU 200 + MMLU 200，多选题，判卷 = 选项字母比对。P13 冒烟实测证明 Qwen3-1.7B 无法被 32 token 预算可靠地压成「只答字母」，因此正式协议改为**保持思考模式开启、max_new_tokens=2048**，在 `</think>` 后的可见结论中抽取答案；前后测始终同参。角色 = 分布外哨兵，专测「通用能力有没有被数学训练带塌」。题量依据：考卷一的使命是**抓小幅退化**（灾难性遗忘通常是 5 个点级别），200 题 95% 置信区间 ±7% 抓不住，400 题 ±5% 才够
- **考卷零（直觉卷）**：手写 10 题，4bit 量化基线 5.5/10——只作体感样例，**不进正式结论**（口径与被蒸馏的 FP16 学生不一致）
- **冻结纪律**：考卷文件、解码参数、prompt 模板、**batch 大小**（**8**——batch 12 在共享 GPU 的笔记本上踩显存悬崖见 P15，batch 8 是 3.5h 全场实测验证过的值；前后测必须同 batch）一次性定死；前测/后测唯一允许变化的只有模型权重（蒸馏）。两张卷 = 两个并列受控实验，分别支撑「域内提升」与「域外不塌」两个结论。性能注记：HF 静态批处理有「尾梅者拖全批」的结构性低效（一条 2048 token 的思考者让同批全部空转 padding），实测约 42 s/题、全场 3.5h；vLLM 连续批处理可再提 5-10×，但 WSL2 装它风险大于两场评测的时间收益，不放本地；长评测一律后台托管 + 日志

#### D8.1 评测脚本的工作原理（七阶段 SOP）

transformers 是引擎，脚本是考务流程（SOP）——引擎只负责吐 token，考试的组织、判分、存档全在脚本里。七阶段：

1. **读考卷**：从冻结 jsonl 读题。脚本从不联网采样——考卷在冻结那一步就定了，谁跑都是同一份
2. **加载模型**：bf16 上 CUDA；有 `--adapter` 再叠 LoRA 小矩阵——这就是后测与前测的全部区别
3. **拼 prompt**：指令 + 题目套 `apply_chat_template`（穿 Qwen3 对话格式外壳）。prompt 的每个字都是协议的一部分，前后测一字不差
4. **批量生成**：`generate(do_sample=False, max_new_tokens=2048)` 内部是循环——每步对全词表打分、贪心取最大（等价 temperature=0）、拼回序列再打分，直到输出结束符或撞上限。模型所谓「思考」就是这个循环逐步蹦 token；batch 12 = 12 条序列同步蹦（并发的来源，也是尾梅者拖全批的来源）；左侧 padding 让长短不一的序列右端对齐，生成永远发生在最右边
5. **抽取**：按 `</think>` 切出可见部分 → 找 `####` 数字 → 降级抓最后一个数字，并记录 `extract_method`——每个答案是怎么抽出来的可追溯
6. **判分**：去逗号/美元符转浮点后**数值**比对（防 `1,080` vs `1080` 格式冤案）
7. **统计落盘**：accuracy / 白卷率 / 步数分层 + 每题原始记录进 JSON——「报告必须存原始输出」的落地

**复用表**（写一次用一辈子）：后测 = 同命令 + `--adapter`，零新代码；换考卷 = 换 `--paper`；换模型 = 换 `--model`。C 层训练完成后仍可复用这两份后测脚本，只需把 `--adapter` 指向新目录；新增代码发生在 C 层训练 loss，不发生在后测。**生态备注**：lm-evaluation-harness / OpenCompass 是现成评测框架，未采用的原因——要自定义白卷率指标、用自己的冻结考卷、完全掌控协议细节；对一周项目，「自己拥有」比「引用黑盒」更符合「理解数据集」考点

### D9 网络与下载路径：数据集与模型权重分开对待

- **数据集（MB 级）**：本地 WSL 下载（`datasets` 库 → 固定 seed 采样 → jsonl），几 MB scp 上远程——**远程不需要为数据集联网**
- **模型权重（GB 级）**：只有 Qwen3-8B 16GB 需要落到远程 910B，三级方案按侦察结果选：
  1. 直连 HF（上机先 `curl -sI https://huggingface.co` 验证）
  2. 不通 → `HF_ENDPOINT=https://hf-mirror.com`（社区镜像，可用性与合规先验证）
  3. 再不通（常见于隔离集群）→ 本地下好 scp 上传，提前按带宽估时

| 数学推理总时长 | 82 min | 13.6 min | 快 6 倍 | 部署视角的意外收益：不再空转 |
| 5-6 步数学 | 0.6615 | 0.7846 | +12.3pt | 训练分布主力区，涨最多——归因干净 |
| 7 步+ 数学 | 0.5714 | 0.50 | -7.1pt | 小样本（~30 题）噪声区间，如实记录 |
| **通用 accuracy（MCQ 400）** | 0.64 | **0.5925** | **-4.75pt** | **遗忘信号，超 3pt 触发线 → 第二轮触发** |
| MMLU / CMMLU | 0.595 / 0.685 | 0.52 / 0.665 | -7.5 / -2.0 | 英文知识受损最重（训练数据全为英文数学链） |

**三个结论**：① 蒸馏核心目标达成——白卷清零 + 域内提升 + 推理提速 6 倍；② 通用知识出现轻度遗忘，MMLU（英文）比 CMMLU（中文）受损更重——与「训练数据全为英文数学链」一致；③ 两次独立运行的 accuracy 逐位一致，协议可复现性自证。

**第二轮选项**（历史决策记录；最终执行 a/e 的 184 条锚点版本）：
- a. 通用锚点混入重训（D7 预案）：COIG-CQIA/ultrachat 采样 100-150 题 → 8B 老师生成 → 混训。最对症，需远程 910B 再跑一轮。**重训 vs 补训**：LLaMA-Factory 支持 adapter 续训（`adapter_name_or_path` 加载 v1 + `create_new_adapter: false` + 降 LR 至 2e-5 + 数学回放 30-50% 混合）——大规模场景下补训省时间，本项目中训练仅 7 分钟，重训归因更干净，v2 首选重训
- b. 超参轻调重训（纯本地 30 分钟）：epochs 3→2 或 rank 8→4——LoRA 扰动减小，遗忘应减轻，域内涨幅可能同步减小；可快速拿到 A/B 数据
- c. 如实交付 + 列后续：一次训练完整暴露「域内提升 vs 通用遗忘」的 trade-off，本身就是高质量实验结论
- d. **零成本实验（无需新数据）**：PEFT adapter 加权缩放——distill-v1 按 0.5× 强度合并，数学增益与遗忘同步回收，可扫出 trade-off 曲线；10 分钟纯推理。若缩放证明「收益/遗忘同旋钮」，则混数据重训是唯一出路；若不是，存在更优配比
- e. **锚点配比 A/B**：锚点数量是配比旋钮——184（29%，数：通 71:29，保数学优先）vs 500（48:52，回收优先）。MMLU val 池 1531 题供给充足、与考卷一 test 天然隔离。**先跑 184 版，数据说话后再按需升级**——通用回到基线则止步，仍在掉则上 500 做配比 A/B

**v2 实测结果（锚点混训，2026-09-27，已完成）**：460 条数学回放 + 184 条 MMLU val 锚点，共 644 条，fresh adapter 重训。考卷二 accuracy **0.79**（vs v1 0.8033，稀释代价 -1.3pt；仍高于前测 +3pt），截断率 0.33%（1 题），5-6 步 0.7231，7 步+ 0.4286；考卷一 accuracy **0.63**，将 v1 的通用遗忘从 -4.75pt 回收到 -1.0pt（噪声内），其中 MMLU 0.52→0.59。恢复部位与 MMLU val 锚点来源精准对应，29% 配比已经足够，因此不再追加 500 条版本。B 线锚点补习在此收官。

### D11 4B 教师对照：决定结果的是推理信号是否保留（2026-09-28）

这条实验线最初想回答「更接近学生容量的 4B 老师会不会比 8B 更好教」。老师端先给出了反直觉证据：同 500 道 GSM8K 种子、同旧模板下，Qwen3-4B accuracy **0.918**，与 Qwen3-8B 的 **0.926** 仅差 0.8pt；4B 改用 `--visible-cot` 模板后为 0.932，但该数字混入了提示词变化，只作补充。由此，学生早期崩盘不能简单归因于「4B 老师能力差」。真正的差异在输出结构：4B 经常把完整推理留在 `<think>`，可见区只剩 `#### N`；若数据管道只拿可见区，就等于把老师会做题的过程丢掉后再交给学生。

| 4B 数据版本 | 数据形态 | 数学 accuracy | 通用 accuracy | 判读 |
|---|---|---:|---:|---|
| 原始 4B（465） | 含 62 条裸答案 | 0.4167 | 0.6225 | 捷径学习：学生学会跳步骤 |
| 误名 clean（460） | 62 条裸答案仍在 | 0.15 | 未测 | 只清格式，没有清内容 |
| canonical 4B-v2（443） | 过滤裸答案并转正 45 条链，cutoff 1024 | 0.5867 | 0.6125 | 数据污染修复后回升 17pt，但过程信号仍不充分 |
| **4B-think（443）** | **保留完整 `<think>` + 可见解答，cutoff 2048** | **0.8233** | **0.6325** | **B 层双卷闭环；逐题 JSON 已入库** |

`distill-4b-think` 相对 canonical 同时改变了训练文本形态和为长文本配套的 cutoff（1024→2048），因此它不是严格的单变量消融，不能把 23.66pt 提升全部归给 `<think>` 标签本身；但它足以推翻「4B 教师容量导致学生学不好」的旧解释。更准确的结论是：**蒸馏能否保留老师实际使用的推理 token，比老师是 4B 还是 8B 更关键。**

考卷二的正式结果为 247/300，accuracy **0.8233**：2-4 步 0.8507、5-6 步 0.7692、7 步+ 0.6429。267 条规范收尾题答对 246 条（0.9213）；另外 33 条撞到 2048 token 上限，按冻结脚本的 `last-number-fallback` 判分，仅 1 条答对。它把长链点估计拉到当前最高，同时恢复了基线式长思考：总耗时 4909 秒（约 82 分钟）、截断率 11%。逐题配对比较中，它相对基线净多答对 19 题（McNemar exact p=0.0019），相对 canonical 4B-v2 净多 71 题；但相对 8B-v1 仅净多 6 题（p=0.4614）、相对 8B-v2 mix 净多 10 题（p=0.2026），所以应表述为**当前点估计最高**，不能声称已经显著超过两条 8B 路线。通用卷已在功能分支 `e1ed686` 完成并归档入当前 `main`（0.6325），不再是待测实验。

### D12 镜像、容器、进程、任务：四层关系（2026-09-29 补记）

远程实验里「新建容器」「启动容器」「点火跑训练」是四个不同层次的动作。本项目踩过一次：以为容器配置改一下就能换卡，实际设备绑定在**创建**那一刻就冻结了，要改只能重建容器。

| 层次 | 是什么 | 本项目实例 | 改得动吗 | 消耗什么 |
|---|---|---|---|---|
| 镜像 image | 只读的文件系统模板（环境） | `quay.io/ascend/llamafactory:latest-910b-ubuntu` | 换镜像 = 换环境，等于重来 | 磁盘 |
| 容器 container | 镜像的一份可写实例 + **资源绑定**（设备、挂载、网络、shm） | `develop-llm-npu` 创建时绑定 davinci0-3 与 `/data` | **创建后冻结**，要改只能删掉重建 | 一点磁盘（可写层） |
| 容器主进程 | 容器里跑着的主进程（`docker run ... /bin/bash` 中的 bash） | 容器显示 `Up` 表示 bash 活着，它本身不干活 | 随时 `docker start/stop` | 几乎为零 |
| 任务进程 | **在容器里另外执行的命令**，真正吃算力 | `docker exec ... python3 -u scripts/kl_train_4b.py` | 随时换参数、随时起停 | NPU 算力 + 电 + 数小时 |

关系链：**镜像 →（创建）容器 →（启动）主进程 →（exec）任务进程**。`docker run -itd ... /bin/bash` 一步完成前两步，所以「新建」和「启动」常被当成一件事，但责任不同：创建决定"能用哪些资源"（不可改），启动只决定"现在活着吗"（随时可切）。

**「启动容器」和「点火」像在哪、不像在哪**：像在**资格**——容器一启动，设备绑定立即生效，能用或不能用（本项目的 `dcmi -8020`）此刻就定了；不像在**消耗**——容器 Up 着但不跑任务，算力和电耗为零。`vllm-ascend` 挂了两天并不等于它在烧卡；但它虽然空转，却一直占着 4-7 卡的映射名额，别的容器再映射这几张卡就会初始化失败。**在这套系统里，容器同时是"环境封装"和"资源占位"两件事。**

**数据放在哪一层**（决定容器删了会不会丢）：

- 镜像层：只读，容器里怎么折腾都不变
- 容器可写层（容器内 `/root`、临时装的包等）：`docker stop` 保留，`docker rm` 全丢
- 宿主机挂载目录（本项目的 `/data` = 宿主机 `/root/data/gdut-yc/llamafactory-npu`）：属于宿主机，容器生死不影响——项目文件、模型、checkpoint、日志都放这里，打包回传也在宿主机侧直接做

**两个实例**：① `llamafactory-npu`（实验室共享）把 0-7 全映射，碰上 `vllm-ascend` 占用的 4-7 就整体初始化失败，因此我们没有改它，而是另起只映射 0-3 的 `develop-llm-npu`，两边共存；② `nohup python3 -u ... < /dev/null &` 是让任务进程脱离终端自己活着——挂在 `docker exec` 交互会话里的任务，会话一退就会被杀（与 P16 的 SIGHUP 教训同源）。

### D13 技术选型登记表：每个决定为什么是这样（2026-10-02 补记）

实验方案里每个技术细节都有一条选取理由，理由分三类，混着写会掩盖薄弱环节：

- **硬约束**——不改就做不成，理由充分；
- **文献/惯例**——有出处，但没有针对本任务验证过；
- **经验判断**——当时拍脑袋，必须配事后验证，没验证的如实标注。

以 top-32 为例：选「只存 top-k」是硬约束（全词表 65GB/老师 vs top-32 压缩后 16MB，差 4 个量级；AOne 传输 1.2MB/s 下全词表单程约 30 小时；vLLM `prompt_logprobs` 接口本身只有 top-k 路径，默认上限 20、需显式传 `max_logprobs=32` 放行），但 **k=32 这个数值是拍脑袋的**（"够大的整数"，比默认 20 大、2 的幂，无针对本任务的推导）。事后补了两件事：覆盖率实测（T=1 下 8B 平均 99.992%、最差位置仅 82.9%）和审计发现的隐患（T=2 摊平分布、放大尾部，丢掉的恰好更重要——采集时没预见）。所以它是"已审计的近似"，不是"已证明无损的等价"，汇报里也只能叫 top-32 条件 KL、不能叫完整词表 KL。

#### D13.1 硬约束驱动

| 选型 | 理由 | 出处 |
|---|---|---|
| 离线 logits 而非在线共驻 | 最初按 24GB 卡规划，8B(16GB)+1.7B(3.5GB) 装不下；远程 910B 虽装得下，但离线已锁定且省重复 forward、信号冻结可复现 | D3.2 / D4.1 |
| top-32 而非全词表 | 存储 65GB→16MB（4 个量级）+ 传输带宽 + vLLM 接口只有 top-k 路径 | 本节 |
| cutoff 1024 | v1 训练集全序列实测最长 759 token，不丢样本 | D6 |
| 评测 batch=8 | P15 实测 batch 12 显存 96.8% 满 → 吞吐跌 10 倍 | P15 |

#### D13.2 文献/惯例驱动（未针对本任务消融，如实标注）

| 选型 | 理由 | 未验证的部分 |
|---|---|---|
| T=2.0、α=0.7、KL×T² | Hinton 2015 起步配置；T² 保证调 T 只改"教什么"不改"学多猛" | K/T/α 网格没跑（K=8/32、T=1/2） |
| LoRA r=8 α=16 dropout 0.05 | B 层 v1 延续，保证 C 层与 B 层可比 | 未扫 r |
| 考卷 300/400 题 | 按 95% 置信区间宽度（±6%/±5%）反推 | — |
| McNemar + bootstrap | 小样本逐题配对的标准做法 | — |

#### D13.3 经验判断 + 事后验证（本项目的修正闭环）

| 选型 | 当时的判断 | 事后验证结果 |
|---|---|---|
| top-32 的数值 | "够大的整数" | 覆盖率实测 99.992% 均值 / 82.9% 最差；T=2 尾部放大是审计时才补记 |
| 思考模式开 + 2048 预算 | 首轮用 32 token 压制失败（P13，12.75% 不可解析） | 改为顺应模型天性后 unparsed 1.5% |
| 停尾 token 监督 | 第一轮实测截断率 75% 异常 → 倒推出训练目标未覆盖收尾位置（D3.4） | 补 `<|im_end|>` 重跑：截断率 75%→0%、准确率不变——修的是行为不是能力 |
| 换设备重测基线 | 预设"前后测必须同设备" | 实测 CUDA→NPU 漂移 −1.3pt/−2.25pt，预设成立 |
| HF/vLLM 双采集器对照 | 担心换工具引入混杂 | top-1 一致率 99.46%，混杂排除 |

#### D13.4 总结：三条选型纪律

1. **每个选型标注类型**（硬约束/惯例/经验判断）——掩盖类型等于掩盖薄弱环节；
2. **经验判断必须配事后验证**（覆盖率测量、异常诊断、对照实验），没验证的如实写“未验证”；
3. **验证发现偏差后二选一**：要么修复重跑（停尾 token、4B 裸答案过滤），要么写进结论边界（top-32 不称完整词表 KL）。

一句话：**选型可以妥协，理由不能含糊——妥协是工程，含糊是隐患。**

### P18 · 清洗只查格式不查内容——62 条裸答案行混入 4B 训练集，学生崩至 0.15

- **现象**：A 线 4B-clean 后测 accuracy 0.15（前测 0.76），生成速度异常快（0.6s/题），visible_tail 中位 7 字符——模型跳过全部推理直接输出「#### 猜测数字」（pred 分布：10×49、100×32 等凑整数）
- **排查**：pred 分布 = 高频凑整数 → 猜测策略；回查训练数据——4B 原始数据含 **62 条 output <100 字符的裸答案行**（最短全文仅 `#### 4`，6 字符），而 8B 数据为 0 条。4B 老师对部分题目只输出了裸答案（无推理链），混入训练集后教会学生「跳过推理直接报答案」；清洗版重训（0.15）比未清洗（0.4167）更差——清洗把 33 条 boxed 补成 #### 行，「直接报答案」模式浓度反而更高
- **解决**：`fix_4b_degenerate.py` 双重过滤（格式统一 + **output <120 字符的退化记录丢弃**）→ 398 条 v2 数据；终验泄漏 0、不合规 0
- **教训**：① **格式合规 ≠ 内容合格**——裸答案行 100% 通过格式检查，却是最毒的样本；清洗必须同时查「格式」和「内容充分性」（长度/结构）；② 数据来源的生成端要有质量下限约束（生成 prompt 应要求详细步骤），否则下游清洗要背上游的锅；③ 异常快的推理速度本身是诊断信号——0.6s/题 = 模型没在思考

### P17 · 清洗脚本两处缺陷：校验只查「包含 ####」+ 未处理「#### 后跟冗余 boxed」 · 清洗脚本两处缺陷：校验只查「包含 ####」+ 未处理「#### 后跟冗余 boxed」

- **现象**：v2 混合数据体检发现 12 条数学记录不是 `#### N` 结尾（尾部是 `oxed{N}` 冗余块）——而清洗当时的校验报告是 0 残留
- **排查**：`clean_train_v1.py` 两处缺陷——① 去重逻辑只删「#### 之后的重复 #### 块」，没处理「#### N 之后又跟 oxed{N}」的组合（12 条正是这种：答案行后面还挂了个 LaTeX 盒子）；② 当时校验用 `HASH_LINE.search`（任意位置命中即通过）而非结尾锚定 `HASH_TAIL.search`——「#### 在文中、结尾是别的东西」的记录全部漏网
- **解决**：`repair_tail`（截断到最后一个 `#### N` 行尾，冗余块/复述句一并去除）修复权威文件 distill_train_v1.json；重建 v2 mix 终验三绿（泄漏 0 / 数学不合规 0 / 锚点不合规 0）
- **教训**：① 校验要锚定「结尾」而非「包含」——包含式校验会把「格式对但位置不对」放过去；② 清洗规则要覆盖「多种答案格式并存于同一条」的组合情况；③ 修复脚本同时写回权威文件，保持所有下游引用一致

### P16 · 拆串行队列时误杀 90% 进度的评测——SIGHUP 会沿前台进程组传播 · 拆串行队列时误杀 90% 进度的评测——SIGHUP 会沿前台进程组传播

- **现象**：用户要求「考卷一晚点自己跑」，我把调度 bash 杀掉以解除自动接续——bash 死亡导致其控制终端关闭，**SIGHUP 广播到前台进程组**，里面正在跑的 gsm8k python（约 90% 进度）被连带终止。旧代码无每批落盘，进度全部损失
- **排查**：`kill 父bash` ≠ 只影响父进程——终端会话退出时，内核向该终端的前台进程组全员发 SIGHUP，默认动作是立即终止（Python 的 atexit/stdio 缓冲都不会执行）
- **解决**：重启 gsm8k v2，用 `setsid nohup ... < /dev/null &` 启动（新会话、无控制终端，SIGHUP 永远打不到）；新代码每批落盘 `.partial.json`，最坏损失 = 一个批次的 12 分钟
- **教训**：① **不要把两个长任务写死在一个串行脚本里**——想拆解耦就得杀进程，正确的形态是每个任务独立脚本、独立启动；② 对「要继续活着」的进程动手前，先确认它的 detachment 状态（有没有 setsid/nohup）；③ 进程的 foreground process group 是一个整体，杀会话头 = 杀全组

### P15 · batch 12 显存悬崖——吞吐量暴跌 10 倍

- **现象**：考卷二 v2 用 batch 12 跑，第一批 44 s/题正常，第二批起 **448 s/题**（10 倍恶化），全场预估 37 小时；进程 CPU 100% 烧了 3 小时只做完 24 题
- **排查**：显存 7927/8188 MiB（96.8% 满，零余量）。WSL2 的 CUDA 走 GPU-PV 与 Windows 桌面共享 GPU——桌面侧（浏览器硬件加速等）的显存波动会把推理挤过临界点，溢出到共享内存后吞吐跳水一个数量级
- **解决**：杀掉重跑。batch 退回 **8**（上一轮 3.5h 全场验证过的配置）+ `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 降碎片；评测改为后台托管 + 全程日志（进度可见才能诊断「卡住 vs 慢」）
- **教训**：① 和桌面系统共享 GPU 时，显存满载率超过 ~95% 就是悬崖，「安全上限」必须按最坏情况（桌面也在吃显存）定义——我上一版笔记把 batch 12 标成安全上限是按理想环境算的，实测环境约束要重新验证；② 长任务必须托管进日志文件，终端里的进度看不见就无从判断卡住还是慢——且 Python 的 print 重定向到文件后走**块缓冲**，进度行会攒着不落盘（tqdm 走 stderr 不受影响），托管长任务要加 `PYTHONUNBUFFERED=1` 或 `python -u`；③ 10 倍量级的性能突变，第一嫌疑是「溢出到慢介质」（共享内存/交换），不是负载变化；④ 监控分三层——死活（py-spy dump 看调用栈 + CPU 时间采样）、健康（nvidia-smi）、**速率**（进度落盘）——「活着但慢爬」只有第三层能发现，评测脚本要每批把部分结果写进 `.partial.json`，进度和断点保护一次解决

### P14 · 截断率 85% 是统计假象——batch padding 污染长度统计

- **现象**：考卷二首轮 `truncated_rate: 0.8533`，与 `accuracy: 0.76` 自相矛盾（真截断的输出连答案都没有）
- **排查**：`generate` 返回的整批序列被 pad 到同一长度；统计用 `len(out_ids)` 数的是**含 padding 的行宽**——批里只要有一条序列跑满 2048，全批 8 条都被误判为截断。判分本身不受影响（解码时 `skip_special_tokens=True` 已跳过 padding）
- **解决**：真实长度 = `(out_ids != pad_token_id).sum()`；同时在报告里存每题回答的可见文本尾部（visible_tail）——**不存原文，出了统计 bug 就只能花 3.5 小时重跑**
- **教训**：① batch 推理里「每条序列的长度」必须排除 padding，这是批处理统计的经典坑；② 两个指标互相矛盾时先怀疑测量而不是模型——0.85 截断 + 0.76 正确在物理上不可能同时成立；③ 评测报告永远存原始输出，报告是可重算的，原始输出不可再生
- **附带信息**：本轮 runtime 3.5 小时（300 题 × 思考模式 × batch 8），远超 30-60 分钟的预估——思考型模型的输出长度要按 1000-2000 token/题估

### P13 · MCQ 评测 12.75% 未解析——给推理型模型设「只准说答案」的协议是设计错误

- **现象**：考卷一首轮跑分（32 token 预算 + 关思考模式），unparsed_rate 12.75%（51/400），accuracy 0.49（MMLU 0.40 / CMMLU 0.58）
- **排查**：抽查 51 条原始输出——模型无视「只输出字母」指令，直接开始解题（"We are given the equation..." / 「我们来分析这个物理问题...」），32 token 截断在解题半路，字母从未出现。重灾区正是数学/物理学科
- **解决**：协议修正为思考模式开启 + max_new_tokens=2048 + 解析加固（取 `</think>` 后可见部分，答案句式优先、字母取最后一次出现，兼容 CJK 邻接字符）。首轮结果作废，定性为**能力下界**而非基线
- **教训**：① 协议设计必须先在 10 题上试跑再全量；② 给推理型模型设「不许思考」的约束是逆天性的，正确做法是让它思考完再解析结论；③ unparse_rate 是判卷器健康度的第一指标，accuracy 之前先看它

### P12 · CMMLU 无法在 datasets 4.0 加载（脚本式数据集被移除）

- **现象**：`load_dataset("haonan-li/cmmlu", ...)` 报 `Dataset scripts are no longer supported, but found cmmlu.py`
- **排查**：datasets 4.0 移除了「数据集加载脚本」机制；CMMLU 的 HF 仓库还是老的 script-based 形态，MMLU 已转 parquet 所以能加载
- **解决**：绕过 HF，直接从 CMMLU 官方 GitHub 仓库拉 67 个学科的原始 CSV（GitHub API 列目录 + raw 下载），逐文件重试 + 失败跳过；抽 100 题并入考卷一
- **教训**：老牌数据集在 HF 上的形态分两代（加载脚本 vs parquet），新版 datasets 库只能吃后者；遇到前者直接去项目原始仓库拿原始文件
- **附带坑**：Git Bash 会把 `~/...` 参数提前展开成本地 HOME，调 wsl.exe 传 Linux 路径一律写绝对路径 `/home/melody/...` 并配 `MSYS_NO_PATHCONV=1`

### P11 · hf-mirror 下载大模型 401 Unauthorized（Xet 后端不走镜像）

- **现象**：`snapshot_download("Qwen/Qwen3-1.7B")` 走 `HF_ENDPOINT=hf-mirror.com` 报 401，域名 `cas-server.xethub.hf.co`
- **排查**：huggingface_hub 1.x 默认用 Xet 协议拉取 Xet 存储的仓库；Xet 的 CAS 重建请求直连官方服务器，镜像无法代理。小模型（Qwen3-0.6B）能下是因为其仓库未走 Xet
- **解决**：`export HF_HUB_DISABLE_XET=1` 回退到普通 HTTP 下载路径（镜像可代理）
- **教训**：镜像站只能代理主站 API 和 LFS 文件，新存储协议（Xet）的直连域名是独立失效点；用镜像时顺手禁用 Xet

### P8 · Git Bash 调 wsl.exe 时内联脚本的变量丢失

- **现象**：`bash -c 'for m in ...; do pip install -i $m; done'` 中 `$m` 展开为空，报 `-i option requires 1 argument`
- **排查**：wsl.exe 重组 Windows→Linux 命令行时，内联多行脚本的引号与变量展开不可靠
- **解决**：复杂逻辑一律写成脚本文件（`bash /mnt/d/xx.sh`），wsl.exe 只负责启动
- **教训**：跨系统调用 shell 时，内联脚本的复杂度上限是「一条命令」

### P9 · Git Bash 的 MSYS 路径转换改写了 WSL 路径

- **现象**：`bash /mnt/d/.../setup.sh` 被 Git Bash 改写成 `bash C:/Program Files/Git/mnt/d/...`
- **排查**：Git Bash 对看起来像 POSIX 路径的参数自动做 MSYS 路径转换
- **解决**：命令前加 `MSYS_NO_PATHCONV=1`
- **教训**：从 Git Bash 调原生 Windows 程序并传 Linux 路径，必须禁用路径转换

### P10 · 清华镜像对单个 wheel 突发 403

- **现象**：`pip install --upgrade pip` 下载 pip-26.2.1 wheel 时 HTTP 403
- **排查**：用 python urllib 探测四个国内镜像，simple 索引页全部 200——是 CDN 对该文件的瞬时限流，不是网络不通
- **解决**：安装脚本内置多镜像回退（阿里→清华→USTC→腾讯），单个镜像失败自动换源
- **教训**：镜像失败≠镜像坏了，探测+回退比死磕单源省时间

### P7 · WSL 内提示 localhost 代理未被镜像（NAT 模式）

- **现象**：进 WSL 时输出 `wsl: 检测到 localhost 代理配置，但未镜像到 WSL`
- **排查**：Windows 侧有 127.0.0.1 本机代理；WSL2 默认 NAT 网络下，WSL 内的 localhost ≠ Windows 的 localhost
- **影响与解决**：目前无害；将来 WSL 里下载 HF 资源时代理不能按 localhost 用。预案：`.wslconfig` 开 `networkingMode=mirrored`，或代理地址改宿主机内网 IP

### P6 · 基线评测两题交白卷（思考死循环撞 num_predict）

> 4096 token 单题诊断只是未纳入正式协议的可选排查，正式前后测仍冻结为 2048；当前结论不依赖该诊断。

- **现象**：Q1（涨价打折）、Q3（袜子抽屉）输出恰好 2048 tokens，正式答案为空
- **排查**：qwen3 默认思考模式，1.7B 在这两题上 `<think>` 内循环，预算耗尽未产出答案
- **解决**：截断判 0 分记录在案；评测协议 num_predict 固定 2048 保前后可比；计划用 4096 预算单测这两题，区分「模型死循环」还是「预算太紧」
- **推广**：老师批量生成数据时同样会出此类残次品 → 清洗规则「`<think>` 未闭合 / 撞输出上限整条丢弃」

### P5 · Ollama 冒烟测试回复为空，eval_count=200

- **现象**：`/api/generate` 返回空 content，token 计数正好等于预算
- **排查**：num_predict=200 全被 `<think>` 块消耗
- **解决**：评测改走 `/api/chat`（`message.thinking` 与 `message.content` 是分开的字段），num_predict 给足预算
- **教训**：「回复为空但 token 计数正常」先查思考模式与输出预算，再怀疑模型本身

### P4 · Ollama 安装器自启进程，绕过 OLLAMA_MODELS

- **现象**：安装完成即有 ollama 进程在跑，默认模型路径指向 C 盘
- **排查**：安装器自动拉起服务；`setx` 设置的环境变量只对**新进程**生效
- **解决**：kill 全部 ollama 进程 → `setx OLLAMA_MODELS=D:\develop-llm\models` 持久化 → 手动带环境变量重启 `ollama serve`
- **教训**：装完任何自带守护进程的工具，先确认它的运行时配置真的生效
